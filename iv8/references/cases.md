# 历史案例与可复用决策

以下是 2026 年 10–11 月实际项目中的脱敏结论，只表示当时验证范围。站点、算法、接口与风控可能变化；先重新捕获当前成功请求。不要将这些案例当作预置目标或自动访问授权。

## 海关知识产权备案库：挑战页、动态请求与隔离执行

2026-09-27 的验证中，iv8 0.1.4 可执行首次 HTTP 412 挑战脚本，生成会话材料后由 Python 发请求得到 HTTP 200 查询表单；完整业务页脚本曾导致原生进程崩溃。因此先隔离子进程，再逐阶段验证验证码、动态参数/请求头、精确查询、分页与图片，不把首次挑战通过当成全链路成功。

后续纯协议实验以 `ISLIKE=` 表示精确查询，`adidas` 得到 14 条、2 页（10+4）和 14 张图片，在 macOS 与 OrbStack Linux iv8 子进程中均完成验证；`apple` 的 3 条另经现有 Mapper 写入独立临时 MySQL，重复保存仍为 3 条/3 张。容器子进程成功不等于完整生产采集器已验收。用户随后要求生产由 Java 完成，不能依赖 Python 进程，因此 iv8 验证脚本不自动成为生产架构。

**适用决策：** 用新会话和当前挑战脚本复现，不复制旧 HAR 的动态值；按挑战、查询、分页、图片、入库、生产部署分别报告。分析代码的临时兼容方案不能覆盖宿主部署约束。

## 盐田登录：建议方案与实测结果分开

2026-09-28 的讨论将 iv8 作为现有 HTTP 登录收到 JavaScript 验证页后的候选补充；当时只有方案分析，没有“已通过盐田验证”的证据。社区版仍需宿主衔接 HTTP、Cookie、跳转和响应，验收应覆盖实际查箱与会话过期恢复。蛇口会话失效是另一个问题，不能推断换用 iv8 即可修复。

**适用决策：** 建议尝试、首次运行、真实服务端通过、业务验收是不同状态；沿用现有登录/查询流程，只对已观察到的 JS 验证阶段做最小实验。

## 报关易 / 91etg：先确定是否需要 JS

2026-10-21 的登录页分析使用 iv8 0.1.4 和虚构数据离线核验：登录字段使用 DES-ECB/PKCS7，前端提供密钥，输出十六进制；验证码原样作为表单字段；`checkUkey()` 在所见登录脚本里主要处理字段和表单提交。不能由名称推断硬件验证，也不能由此推断登录后的所有接口。

整页旧 jQuery 初始化发生递归错误，提取最小登录函数后可验证加解密往返和提交参数。后续实际列表 `listData.action` 返回普通 HTML，从 `#info_list` 提取记录及状态，7 条记录与页面逐条一致；普通查询可由 HTTP + HTML 解析实现，无需 iv8 常驻。

另一个详情流程调用电子口岸 `EportClient.signData`，签名输入含卡号和单据编号。iv8 mock 证明的是调用与传参，不能替代真实卡和客户端签名。普通列表可取不代表硬件签名详情已跑通。

**适用决策：** 登录字段、列表协议、详情签名分别验证；有硬件依赖时明确保留宿主客户端；全页不兼容先做最小函数实验。

## 阿里一达通：浏览器登录与独立 HTTP 分工

2026-10-23 的观察中，列表使用 `POST /ptnProvider/customs/list.json`，表单携带 `json` 参数；iv8 执行提取的构造代码证明主要为 URL/form 编码及 `_tb_token_`、`ctoken`、可选 `_csrf_token` 附加，所见业务参数无需额外解密。

验证按阶段推进：最初只是 Chrome 会话内重放；之后才验证了独立 Python HTTP 复用现有会话并读取 50 条商品。独立登录受 `FAIL_SYS_USER_VALIDATE` / `RGV587_ERROR` 拦截，因此采用真实浏览器登录、人工验证、保存并校验会话、独立 HTTP 查询。不能把独立取数成功写成独立登录也已成功。

业务实现由 Java HTTP 层复现已核验的编码，无须额外部署 iv8。后台验证会话按用户/账号隔离，处理过期和并发覆盖；预览查询与导入业务记录是不同操作。

**适用决策：** 动态 JS 只在确有需要时保留；将验证窗口、会话更新和恢复查询设计成完整流程；不得把“使用 iv8 分析”误写成生产运行依赖。

## FastMoss：签名正确不等于请求通过

2026-11-12 项目在 Python 3.12/macOS arm64 环境安装 iv8 0.1.4。提取的签名模块可在 iv8 执行，`fm-sig` 与 Chrome 捕获值一致，`fm-sign` 也完成对照；独立 HTTP/1.1 请求仍返回 HTTP 200 / `MSG_SAFE_0001` 并触发验证。

随后人工验证、刷新会话、补齐实际请求头并启用 HTTP/2，第一页和第二页各取到 10 条且与 Chrome 一致。多项因素同时变化，不可归因于 HTTP/2 一项；后续请求仍出现风控，第 3 页暂停，完整 500 条和长期稳定性未被证实。

用户指出命令行不能让人操作滑块，采集器因此增加内嵌浏览器/专用外部浏览器选项、验证后的会话更新、分页断点续采及全字段导出。每页原始响应、重复观测与去重表分别保留，不能用去重后数量冒充抓取条数。

后续曾针对腾讯滑块做一次本地 OCR 与实际提交验证，成功后取得业务码 200；这只说明该道题的结果，不能证明通用可靠性，也不是本 skill 的默认方案。此 skill 默认暂停并引导人工完成验证，不携带验证码识别依赖。

**适用决策：** 离线签名、真实请求、分页、GUI 验证流程和全量稳定性分别验收；遇到风控停止原样重试，保留进度并更新会话。

## 结论检查表

| 已有证据 | 可以声称 | 仍需验证 |
| --- | --- | --- |
| 离线环境探针成功 | 指定解释器能运行这些 API | 目标脚本、整页兼容 |
| 目标签名与捕获值相同 | 同一输入的签名等价 | 时效、会话与服务端风控 |
| Chrome 内请求成功 | 浏览器会话可访问 | 独立 HTTP |
| 独立 HTTP 一页成功 | 该会话/条件下取数成功 | 独立登录、更多页、长期运行 |
| mock 硬件签名函数 | 调用/参数路径可复现 | 真实设备签名与业务响应 |
