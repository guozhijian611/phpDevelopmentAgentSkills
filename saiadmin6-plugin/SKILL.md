# SaiAdmin 6.x 插件开发

目标是可从 ZIP 在干净 SaiAdmin 6 环境安装的插件，验证前后端、数据库、权限与安装生命周期。所有容器操作使用当前任务的临时 Compose 项目；用户已授权的临时测试可直接执行，不向现有服务导入试验包。

## 先确定契约

1. 读取目标仓库规则、composer.lock、实际 `plugin/saipackage` 和前端 package.json。确认 SaiAdmin/saipackage 都是 6.x，记录版本、基线提交和前端目录。仅看线上 `/plugin/` 文档会误用 5.x 路径。
2. 阅读 [插件契约](references/plugin-contract.md)。目标安装器的 `getAllowedPath()`、`unpack()`、`install()`、`uninstall()` 是包路径和状态转换的事实源；运行副本与 vendor 可能不一致，勿用更新依赖覆盖本地补丁。
3. 新插件在隔离开发副本运行 `php webman sai:plugin <app>`；已有插件保留自身约定。按现有 BaseController、BaseLogic、BaseModel、验证器和权限中间件开发，勿假设命令会生成业务 CRUD。

## 前端主题与多语言（必须遵守）

生成或修改前端代码前，必须阅读 [前端集成约定](references/frontend-conventions.md)，检查目标宿主的主题变量、明暗切换、组件封装、语言注册和翻译调用方式。以目标项目实际实现为准，不自行另建主题或语言系统。

- 插件后台页面沿用宿主布局、组件、语义样式与主题变量；禁止用固定颜色或全局样式覆盖宿主主题。
- 新增界面文案接入宿主 i18n，覆盖宿主已支持的语言；运行时切换语言后，标签、表头、提示和校验信息必须同步更新。
- 语言资源及加载代码必须包含在可安装 ZIP 的允许路径内，验证全新安装能正确加载，不能仅在开发仓库手工注册后宣称完成。
- 明暗主题、可配置主题色与语言切换属于前端验收项；未实测须说明，不能用构建通过替代。

## 安装、升级自动接入（默认要求）

开发插件前必须阅读 [自动接入与卸载](references/automatic-integration.md)。语言注册、插件入口和其它必要宿主接入应随发行 ZIP 在安装、升级时自动完成；正常使用不得要求用户手工修改宿主或额外运行接入脚本。

- 优先使用宿主已有的插件发现/注册机制或正式生命周期钩子；没有合适钩子时，在核实执行顺序后通过版本迁移调用插件自己的幂等接入服务。不要为此默认修改核心安装器，也不要在应用启动、配置加载或迁移 init 中隐式写宿主。
- 修改宿主文件前完整预检并备份；只管理插件自己的最小片段。重复执行不叠加，升级保留业务数据并按需接管已知旧接入；接入契约变更追加迁移，不修改已执行的历史迁移。
- 卸载按既定数据策略先检查，再清理自身片段，保留其它用户改动；不能用旧文件整份回盖宿主。不支持的结构、不可写文件或被改动的管理片段须明确失败，不静默跳过或伪造安装成功。
- 手动预览/修复工具只能作为可选诊断入口。宿主原有的依赖安装、管理端构建流程仍需如实说明，不能将自动源码接入宣称为自动构建或部署。
- 用最终 ZIP 验证无手动接入的首装、升级、卸载与恢复；不能先运行修复脚本再把环境算作自动接入通过。

## 开发与打包

- 后端放 `plugin/<app>/`；6.x 常用前端路径 `saiadmin-artd/src/views/plugin/<app>/`。安装器通常只复制这两个子树，包里另放 `src/api`、`src/router` 不会自动安装。共用接口辅助代码可放自身 views 子树，或明确提供受支持的集成方式。
- 数据库、菜单、按钮权限和字典同时纳入安装及卸载逻辑。迁移、SQL、数据保留策略按 [插件契约](references/plugin-contract.md) 选择。支持哪些数据库必须实测声明。
- `info.ini` 必须声明 `support = 6.x`，管理端安装前会检查；仅通过后端安装不能证明UI可安装。
- 使用专用 staging 目录只放发行文件；`info.ini`、`config.json` 位于 ZIP 根层，没有额外的 `<app>/` 外壳。运行 `python3 scripts/package.py STAGE --zip /absolute/path/app-version.zip`，按目标前端目录传 `--frontend`。
- 打包器是结构检查，不证明 SQL、PHP 或运行时正确。记录 SHA256，并仅用该 ZIP 做导入验收；不得以手工复制源码替代导入测试。

## 隔离验证

按 [Docker 实验室](references/docker-lab.md) 创建每轮全新的环境。`scripts/lab.py create` 不修改源项目，返回临时目录；通过 `compose LAB ...` 限定后续操作的项目边界。PHP 镜像可构建附带 Dockerfile，或显式选用已验证包含所需扩展和 Composer 的本地镜像。使用 `--db mysql|pgsql` 选择独立数据库，详见实验室文档。默认不复制 vendor，可用 `--copy-vendor` 从准备好的干净基线复制依赖。

依照 [验收矩阵](references/acceptance.md) 至少完成：首次安装、同版本重复上传行为、卸载再安装、另一全新环境再次安装；有升级需求时加旧版→新版和新版全新安装。保留成功断言和失败证据。失败重试前检查文件/数据库/安装状态，修包后换干净实验室；同一未知失败最多原样重试一次，不盲目反复执行 SQL。

用 `python3 scripts/build_example.py --output-dir OUTPUT` 生成两版示例包；用 `python3 scripts/self_test.py` 做独立可迁移性检查。可用 `assets/phinx-fixture/` 作为双数据库测试基线：包含菜单、种子和两次迁移，示例业务数据仅用于一次性环境。

## 交付

提供 ZIP、校验值、支持版本/数据库、所用基线与实际验收结果。区分容器启动、逻辑层验证、HTTP 上传、浏览器业务验收；未执行的项目明确标记。实验室结束只对记录的项目执行 `down -v --remove-orphans`，不运行全局 prune。保留需用户验收的实验室及访问地址，销毁其余测试容器；临时目录可留作证据。

## SaiStore 开发者后台上传

用户要求上传到 SaiThink 开发者后台时，先读 [登录与上传 CLI](references/saistore-upload.md)，核对目标站点、应用 ID、最终 ZIP 和更新日志。使用 `scripts/saistore.py`：无有效登录时提示用户在本机交互终端输入用户名、密码和图形验证码，成功后按站点隔离保存 access/refresh token；后续命令自动读取本地会话，不在聊天索要密码、输出令牌或把凭据放入工作区。

验证码由用户读取图片后输入，禁止利用响应中的 result 字段代答；密码仅通过隐藏终端输入且不保存。默认验证 HTTPS，当前后台的 HTTP 访问需显式 --allow-http，不自动忽略证书错误。非交互环境缺少登录时，提供准确的 auth login 命令，让用户在本机终端完成，不能伪造登录或导出浏览器凭据来替代 CLI 登录。

先 `upload --dry-run` 形成明确计划，再按用户已经授权的上传范围执行。区分应用草稿、图片上传、ZIP 文件上传、版本记录、提交审核与审核通过；只要求上传时不自动提交审核。检查重复版本和应用标识，读回版本确认成功；未知写入结果不得盲目重试，按私有回执核对后使用 --resume。保存 refresh token 不等于已验证刷新接口；当前未发现可确认的刷新路由，令牌过期重新登录，不猜测接口。

来源与本次验证范围见 [sources-and-validation.md](references/sources-and-validation.md)。
