# 系统权限点与 DataScope 接入

## 先分清三类约束

| 约束 | 决定什么 | 插件接入位置 |
|---|---|---|
| 账号、角色、菜单、按钮/API 权限 | 能否进入页面、执行某个动作 | 宿主认证/权限中间件、Controller 权限声明、菜单按钮记录、前端权限指令 |
| 角色数据范围 | 已获准的动作能操作哪些记录 | Logic 查询与写入、角色 data_scope、部门关系、身份缓存 |
| 业务归属与租户 | 客户、项目、负责人、租户之间的业务边界 | 服务端业务条件，与上面两层同时满足 |

前端权限指令只影响交互，接口必须独立鉴权。角色“全部数据”只解除该层的数据范围过滤，不能解除租户/业务边界。公开发布链接、HTTP 数据源代理等另有访问策略，不应因为没有后台身份就退回全部数据。

## 开发前核对实际宿主

逐实体记录归属字段、共享策略、适用的数据范围及全部读写入口。订单等有归属的数据默认接入；真正全局共享的字典/配置可不按创建者过滤，但仍需功能权限与适用的租户限制。负责人/客户权限不等同于 created_by；采用其它策略时明确映射与测试，不能新增一个无效字段就算接入。

检查以下实际实现，而非仅看包名或后台存在“数据权限”按钮：

- 认证/权限中间件覆盖的路由；`BaseController::init()`、Logic 身份初始化、自定义接口是否遗漏 `Permission`；继承基类不代表任意路由已鉴权。
- 当前 ORM 的 BaseLogic 是否存在 `$scope`、`userDataScope()`，哪些方法调用它。参考包只有 ThinkORM 版，不能假设 Eloquent 具有相同能力。
- 业务表、Model 及迁移中的 created_by、主键、别名；插入事件是否可靠地以服务器身份赋值、只读字段是否阻止普通更新。原始 SQL、批量 insert、导入可能绕过 Model 事件，须单独处理。
- 角色 data_scope、角色—部门关联、用户部门及子部门树是否齐全；身份/菜单/按钮缓存如何失效。无身份、无角色、无部门、空自定义范围及无效枚举默认拒绝或返回空集合；管理员豁免只按宿主明确的服务端身份策略实现。
- 多角色组合规则必须明确并验证；不是简单数值大小就能证明包含关系。沿用宿主受测策略，不擅自改成并集扩大权限。Logic 或权限服务复用时不得残留上一账号的 ID/范围，不用共享可变状态保存请求身份。

缺少 DataScope 时，使用已确认的正式依赖或插件命名空间内的适配，随安装/升级自动检查及接入；无法支持的宿主在变更前明确报错。不要自动覆盖整份核心 BaseLogic/角色页面，或假装 `$scope` 属性在不支持的基类上会生效。依赖/共享权限与插件自身菜单的所有权分开记录。

## 菜单、按钮与 API 权限点

1. 按宿主编码约定建立插件自己的页面及操作点，覆盖实际提供的 list/read/save/update/destroy、导入导出、发布等动作。使用稳定唯一编码查重、显式列名和动态父节点定位，不猜菜单/角色 ID；所有普通角色不默认获得全量授权。
2. 后端声明与前端使用同一权限码，并确认中间件真的执行该检查。例如目标支持此语法时，使用 `plugin\saiadmin\service\Permission` 的 `#[Permission('导出记录', 'example:admin:record:export')]`，对应按钮 `v-permission="'example:admin:record:export'"`。这是接入片段；命名、路由及翻译遵循实际宿主，不当作完整可运行模块。
3. 复用系统角色数据权限入口。参考包读取 `GET /core/role/getDeptByRole?id=...`，保存 `POST /core/role/dataPermission`，字段 `id/data_scope/dept_ids`，后端权限码均为 `core:role:data`。仅核对对应宿主后使用，不在每个业务插件复制该入口。
4. 自身菜单/动作点首装注册、升级追加/调整，保持已有用户授权；关系/权限缓存按宿主方式失效。卸载只删自身节点、关系和缓存，不删共享 `core:role:data`、角色、部门及其它插件授权。不要以全局清空角色权限代替接入。

若开发或修改授权管理接口，还须验证操作者可管理目标角色、可授予的菜单/部门子集、data_scope 枚举和无效 ID；有“配置数据权限”按钮不代表可任意扩大他人权限。只开发业务 CRUD 时复用宿主配置，不无端新增授权管理接口。

## 五种数据范围与查询接入

以下是给定 DataScope 包的字段和语义，目标版本应重新核对：

| data_scope | 范围 | created_by 过滤依据 |
|---|---|---|
| 1 | 全部 | 此层不增加过滤 |
| 2 | 自定义部门 | 所选角色关联部门下的用户 ID |
| 3 | 本部门 | 当前用户所在部门的用户 ID |
| 4 | 本部门及子部门 | 当前部门与子部门的用户 ID |
| 5 | 本人 | 当前用户 ID |

包中实际查表为 `sa_system_role_dept`、`sa_system_user`、`sa_system_dept`。部门范围按创建者当前所属部门计算，不是业务记录保存时的部门快照；如业务需要历史归属，应单独建模。不要把示例表前缀硬编码进不同宿主。

确认兼容后，适用实体的 ThinkORM Logic 显式设置 `protected bool $scope = true;`，并检查重写方法与 SaiCode 再生成是否丢失接入。

升级旧表新增归属字段时用新迁移，明确历史记录的归属映射、缺失归属处理与索引；不能把所有历史行默认归给安装者，或使用空/0 归属后宣称数据范围正确。数据库字段存在与数据可信是两个验收项。

| 参考包方法 | 实际覆盖 | 开发要求 |
|---|---|---|
| getList / getAll | scope=true 时查询前加范围 | 列表、选择器、全量与导出优先复用；统计/分页总数也必须受限 |
| read / edit | 对查找目标的查询加范围，再读取/保存 | 自定义覆盖不能绕回未过滤的按 ID 查询/更新 |
| destroy | 回调内过滤待删 ID | 混合有权/无权 ID 可能只删除部分，不得返回“全部成功”；明确整批拒绝或逐项结果 |
| search | 只应用搜索器 | search 后直接 select/count/sum 不自动受限 |
| add | 只调用 Model create | 需验证 Model 赋值/只读约束及业务准入，不能宣称已自动校验创建权限 |

例如在已启用、兼容的业务 Logic 方法内，普通导出可用 `$this->getAll($this->search($filters))`；自定义聚合需先 `$query = $this->userDataScope($this->search($filters));`，再执行 `$query->sum('amount')`。这些是已有 Logic 内的调用片段；只允许白名单过滤项，仍叠加租户/业务条件。不要在已经自动过滤的路径重复调用，也不要先查出全量后在 PHP 或前端过滤。

- 自定义 SQL、联表、子查询、聚合、批量、软删恢复、附件下载、复制/发布与父子资源逐一接入；权限过滤在数据库聚合、分页之前生效。联表时参考实现的裸 `created_by` 可能歧义，核对别名感知的适配或从受限主表子查询关联；不要猜一个不存在的别名参数。
- 写入在受限记录/带范围的条件上完成；不要先校验某 ID，再执行无条件批量 update/delete。将用户 OR 搜索条件分组，保持与权限/租户条件的 AND 关系，防止搜索放宽范围。
- 新增/导入的 created_by 来自可信服务端身份，普通修改白名单排除所有者、租户等归属字段；独立的转交动作须单独授权并校验目标。子记录、附件等通过受限父资源验证，不能仅校验提交的 parent_id 存在。
- 导出任务、队列及缓存显式携带并重新验证适用的身份/范围，不能把 HTTP 缺少身份当作管理员。缓存键/失效包含用户、租户及范围变更，避免把管理员结果复用给普通账号。

## 参考包中不能照搬的细节

这是源码观察，要求开发时处理；不表示原包已修复或所有 SaiAdmin 版本都有这些行为。

- `role/index.vue` 数据权限按钮用了 `core:role:menu`，后端却检查 `core:role:data`。接入目标须统一为真实的数据权限码，并验证“仅菜单授权/仅数据授权”两个账号。
- BaseLogic 的初始范围是 1，空 roleList 返回无范围查询；复用同一 Logic 时 public userIds 持续合并不清空。应拒绝无有效角色，按调用局部计算范围，至少测试连续切换账号，不能仅为通过列表测试开启 scope。
- 多角色选择最大的数字 data_scope，且只取该次选中的一个 role_id；全部 1 + 本人 5 最终是本人，自定义 2 相同时只取先选中角色。不要写成“多角色自动取并集”或“总能得到最严格范围”。
- add 本身不注入或锁定 created_by。已核对的 SaiAdmin 6.1.5 基线 BaseModel 有插入事件与只读 created_by，但不代表所有模型/直接 SQL 都受保护；应实测伪造创建者及修改归属。
- install.sql 是固定菜单 ID 39/父 ID 6 的 MySQL 全列 VALUES，不能直接用作新插件迁移或 PostgreSQL 脚本。包没有 info.ini/config.json，是核心/角色界面覆盖型参考材料，不是可直接导入的业务 ZIP。
- 角色保存数据范围后调用 `UserInfoCache::clearUserInfoByRoleId()`；菜单授权另清按钮/菜单缓存。自有接入须核对对应失效链。给定数据权限 Controller/Logic 方法未显示完整的目标角色级别、枚举和部门子集校验，结合真实中间件/校验器检查，不能据此断言全站已存在或不存在越权漏洞。

## 最终 ZIP 的权限验收

在独立实验室建 A 部门、A 子部门、B 无关部门，以及同部门两名用户创建的记录。使用具备同一业务动作权限的普通账号分别验证 1–5 范围；自定义只选特定部门。至少另设“有菜单无动作权限”和“无菜单及动作权限但直接请求接口”的账号，不用管理员单账号代替。

- 列表、总数、详情、导出、统计结果一致；直接访问他人 ID、修改、删除、附件/子资源、混合 ID 批次不能越权，也不泄露越权记录存在性/内容。
- 伪造 created_by/租户/父 ID、普通修改所有者不生效；测试无角色、空自定义部门、缺失部门、无效范围、多角色组合及同实例跨账号查询。
- 修改角色范围、角色部门、用户部门及授权后，旧会话按宿主策略及时生效；缓存不串账号。存在授权配置能力时测试越级管理/扩大部门及菜单范围。
- 首装/升级权限点无重复、旧角色授权保留，卸载保留共享角色与数据权限入口。MySQL/PostgreSQL 支持声明分别有对应迁移与业务查询证据。

逐实体标注通过/失败/未测/不适用及原因。共享资源的非创建者策略需有实际测试；“已安装数据权限插件”不等于业务已受控。附带 Phinx fixture 只验证生命周期；新增 [权限 fixture](permission-example.md) 演示七动作、五范围、归属保护及升级授权，不代替任意实际插件的业务验收。

## 业务接入实测补充

- Element Plus fragment 下拉项与动态弹窗必须实测 v-permission；必要时用宿主响应式 store 的 v-if，不把模板有指令当成按钮验收。角色授权树还须翻译菜单语言键，详见 [实测排错](runtime-pitfalls.md)。
- 数据范围、资源 ACL 与已发布观看独立建模，SQL 中取适用条件的交集；后台“全部”不能自动取得连接凭据或登录观看权。
- 新建和修改分离后，save 不接受已有 ID 顺带更新；旧更新曾用 save 权限时按实际旧 API 关系迁移。新点仅从对应旧授权映射，重复接入不恢复已撤销关系。
- 缓存命中前重新检查身份/授权/范围，业务写入白名单同时保护版本、草稿和发布指针。不能只保护 created_by。
- 从“非管理员仅本人”升级到角色范围是行为变化，明确提示 1 全部/5 本人；保留原字段值，不擅自将所有角色统一改成某个范围。相同自定义范围固定选取顺序，不能暗示最大数字一定代表权限集合最严格。
- 需要新增角色树或后端兼容接入时追加迁移，全部目标一起预检/回退；卸载在所有业务表保护检查之后再清理。
